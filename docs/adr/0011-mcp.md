# ADR-0011. gtr mcp: the MCP server for Claude

Status: **Accepted** · 2026-11-09

## Context

Claude Code and Claude Desktop work on Go projects with the go command. In a gtr project
that goes wrong in predictable ways: `go get` and `go mod tidy` edit a `go.mod` that gtr
generates, the Go on the PATH is not the one `engines.go` asks for, and go's errors come
without gtr's hints. The Model Context Protocol lets a tool offer its commands to an
assistant with typed arguments, so the assistant can use gtr itself.

## Decision

1. **`gtr mcp`** in the launcher serves MCP on stdio (newline-delimited JSON-RPC 2.0;
   stdout carries only protocol messages, diagnostics go to stderr). It has no
   dependencies: the protocol is small enough to implement in `internal/mcp`.
2. **Protocol revisions.** The server is dual-era: `initialize` negotiates 2025-11-25,
   2025-06-18, 2025-03-26 or 2024-11-05 (an unknown version gets 2025-11-25); a request
   whose `_meta` has `io.modelcontextprotocol/protocolVersion` 2026-07-28 is served
   statelessly (`server/discover`, `resultType`, `ttlMs`/`cacheScope`, serverInfo in
   `_meta`), and another version in `_meta` gets `UnsupportedProtocolVersion` (-32022)
   with the supported list. Batches are refused. Capabilities: tools and resources; no
   prompts, sampling, roots or logging (the last three are deprecated in 2026-07-28).
3. **The root.** The server works in one project: `--root`, else `CLAUDE_PROJECT_DIR`,
   else the working directory — moved up to the nearest `gtr.json` and further to a
   workspace root (a `gtr.json` with `workspaces`). Every tool takes `dir` relative to
   the root (a member); absolute paths, `..` and symlinks that leave the root are
   refused before anything runs.
4. **Tools run the gtr executable itself** (`os.Executable`) in that directory, so they
   go through the same launcher as a person's command: the project's Go and gtr-manager,
   `GOTOOLCHAIN=local`, gtr's error hints. Children get `GTR_MCP=1`, `NO_COLOR=1`,
   `TERM=dumb` and no stdin (no prompts: `gtr login` is not a tool). A tool that ran and
   failed is a tool result with `isError` and the exit code, so the model reads the error;
   a refused argument is a tool error too, a malformed request a JSON-RPC error.
5. **What is available.**

   | Kind | Tools | Annotations |
   |---|---|---|
   | Read | `project_info`, `list`, `why`, `outdated`, `search`, `info`, `env`, `doctor` | readOnly |
   | Change | `add`, `remove` (destructive), `install`, `update`, `sync`, `link`, `unlink`, `version_bump` | not readOnly: clients ask |
   | Run | `run`, `test`, `build` | not readOnly |
   | Release | `publish`: only `--dry-run` unless `--allow-publish`; `self_install` only listed with `--allow-self-install` | destructive, openWorld |

   Not tools: `new`, `init` (one-off, interactive), `dev` and `--watch` (they do not
   end; `run dev` stops at the time limit), `login`, `yank`, `owner` (account actions
   for the person), `self use/uninstall/update/link/prune` (the person's machine). The
   list has a fixed order (clients cache it).
6. **Results.** Text content is the command's output; `structuredContent` adds
   `command`, `dir`, `exit_code`, `output`, `truncated`, `timed_out` and, per tool,
   parsed data: `list` and `outdated` run with `--json` (`packages`), `env --json`
   (`env`), `test` parses go test's summary and gtr's coverage table (`packages` with
   status, time and coverage; `coverage` with min and ok; `failed_tests`).
   `project_info` is answered in the server: `gtr.json`, `locked`, workspace `members`,
   `scripts`, gtr env, the gtr version. Resources: `gtr://gtr.json`, `gtr://gtr.lock` (of
   the root) and `gtr://schema` (embedded).
7. **Limits.** Output keeps its first 8 KiB and last 56 KiB (the end has the summary and
   the error) with a note of what was left out. Time limits: 2 minutes for reading
   tools, 5 for changes, 10 for run, test, build and publish; `timeout_seconds` up to
   an hour. At the limit, on `notifications/cancelled` or when stdin ends, the whole
   process tree is stopped (a process group on Unix, `taskkill /T` on Windows). With a
   `progressToken`, output lines go out as `notifications/progress` (at most four a
   second). Tool calls run concurrently; other requests are answered in order.
8. **Distribution.** `gtr mcp --print-config` prints the `mcpServers` entry for this
   binary and project; `claude mcp add gtr -- gtr mcp` registers it in Claude Code.
   The gtr repository is a Claude Code plugin marketplace (`.claude-plugin/`) with the
   plugin `plugin/`: `.mcp.json` running `gtr mcp --root ${CLAUDE_PROJECT_DIR}`, an
   `allow_publish` setting, and a skill that tells Claude to use gtr instead of go
   get/go mod tidy in projects with `gtr.json`. `gtr mcp bundle` writes a Claude Desktop
   extension (MCPB, manifest 0.3): the running gtr binary and a manifest whose settings
   are the project folder and `allow_publish`.

## Consequences

- The assistant gets the same behaviour as the terminal, including Go version
  selection and hints, without a second implementation of any command.
- New gtr-manager commands become tools only when added here; tools that need
  structured output need `--json` in gtr-manager (`list`, `outdated` and `env` have it;
  `why` and `info` are text for now).
- The Desktop extension contains a copy of gtr for one platform; it uses the same
  `~/.gtr` home as the installed one.
