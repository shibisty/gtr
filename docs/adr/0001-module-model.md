# ADR-0001. Module model: gtr.json is the source of truth, go.mod is generated

Status: **Accepted** · 2026-10-09

## Context

gtr is an alternative to Go modules: dependencies are declared in `gtr.json`,
installed with the `gtr` command and imported by short names. The Go toolchain,
however, only understands `go.mod`. Hiding `go.mod` from the developer is neither
possible nor desirable: IDEs, gopls, CI and the developer all see it.

The prototype ([docs/prototype/bridge](../prototype/bridge/README.md)) showed that
the approach with `replace` directives pointing to local directories works, but it has requirements.

## Decision

1. **`gtr.json` is the single source of truth.** Everything gtr writes to
   `go.mod` is derived from `gtr.json` and `gtr.lock`.

2. **gtr generates `go.mod` in the project root** (and `go.work` for workspaces).
   The file is open and readable and starts with a header:
   ```
   // generated by gtr from gtr.json — edit gtr.json or run `gtr sync`
   // gtr:hash sha256:<content hash>
   ```
   The format is canonical: direct dependencies in the first `require`, transitive
   ones in the second with `// indirect`, each `replace` on its own line, everything sorted.
   `go mod tidy` leaves such a file unchanged (verified).

3. **Every package gets a generated `go.mod`.** A `replace` target must
   contain a `go.mod`, otherwise go fails. Packages are published without `go.mod`; gtr
   creates one when extracting into the store (`module <name>`, `go <engines.go>`,
   `require` for its dependencies). If a package already has a `go.mod` (for example,
   an external Go module), gtr leaves it alone.

4. **Packages live in `gtr_modules/`** in the project root as links into the store
   (a symlink, or a junction on Windows); `replace` points to `./gtr_modules/<name>`.
   Relative paths keep `go.mod` portable between machines, and jumping to a
   package's code from the IDE lands in an obvious place inside the project.
   External Go modules live in `gtr_modules/.go/<module>@<version>`.

5. **go is always invoked through gtr with a fixed environment:**
   `GOPROXY=off`, `GOFLAGS=-mod=mod`, `GOWORK` set to the generated `go.work`
   or `off`, `GOROOT` and `PATH` pointing to the Go version from `engines.go`.
   `go.sum` is not needed: go does not maintain it for directory `replace`s.
   Integrity is provided by `gtr.lock` (ADR-0004).

6. **Manual edits to `go.mod` are allowed but detected.** gtr checks the hash
   in the header against the content. On a mismatch, every gtr command stops
   and offers:
   - `gtr sync` — carry the changes over to `gtr.json` (a new `require` →
     a dependency; a new `replace` to a path → a `file:` source), then
     regenerate the file;
   - `gtr sync --force` — overwrite `go.mod` from `gtr.json`.

7. **Whether to commit `go.mod`.** By default `go.mod`, `go.work` and `gtr_modules/`
   go into `.gitignore` (gtr adds the lines on `init`). The
   `"gomod": "commit"` option in `gtr.json` keeps `go.mod` in the repository so the
   project builds without gtr too, provided `gtr_modules/` is also available
   (for example, in CI after `gtr ci`).

8. **go errors are translated.** gtr recognizes known go messages and
   shows clear ones instead:
   - `malformed module path "X": missing dot in first path element` →
     "package X is not installed, run `gtr install`";
   - `ambiguous import: found package X in multiple modules` on a clash with the
     stdlib → "the name X is taken by the standard library" (see ADR-0002);
   - `module lookup disabled by GOPROXY=off` after `go get` →
     "add dependencies with `gtr add`".

## Consequences

- The project builds with a plain `go build` inside the gtr environment, and IDEs work with
  a real `go.mod` without plugins.
- gtr fully controls downloads: go never touches the network.
- A `go.mod` has to be generated for every package in the store, and the store must stay
  immutable (ADR-0005).
- Open: gopls behaviour (stage 3), junctions on Windows (stage 3), `go.work`
  for workspaces (stage 4).
